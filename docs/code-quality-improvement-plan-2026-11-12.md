# TraceWitness 代码质量完善方案

**编制日期：** 2026-11-12  
**输入基线：** `main` / `f3dbb45`  
**审计依据：** [code-quality-audit-2026-11-11.md](code-quality-audit-2026-11-11.md)  
**项目边界：** 纯软件仿真，不连接真实摄像头、门禁、电梯或厂商硬件

---

## 1. 总体判断

现有审计报告可以作为当前质量基线，主要结论可信：

- Mock 软件原型可构建、可运行、可演示。
- 上传安全、请求体校验、安全响应头、Java 21 构建保护等明确问题已修复。
- 真实 LLM / Agent 尚未验收，因此不能声明“真实 Agent 已完成”。
- 当前最准确的对外表述仍是“独立实现可运行的视频事件调查软件原型”。

但审计报告仍未形成完整的工程质量闭环。主要缺口不是已有结论错误，而是以下内容尚未量化或自动化：

1. 没有测试覆盖率、静态分析、依赖漏洞和许可证扫描。
2. 没有把 HTTP 有状态链路、浏览器回归和 `run_eval.bat` 串成统一质量门禁。
3. 真实模型工具描述、失败重试、延迟、令牌成本和固定任务集尚未工程化。
4. 没有评估并发写入、网络失败、服务重启、数据库升级和备份恢复。
5. API 仍缺少机器可执行的 OpenAPI 契约、统一 DTO、认证和跨 run 写隔离。
6. 审计报告将“代码质量”和“正式验收”混在同一结论中，报告结构可进一步拆分。

审计报告自身有一处计数不一致：第 1 节写“修复了 8 个低风险问题”，第 13 节实际列出 `F-01` 到 `F-09` 共 9 项。后续修订应改为“修复 8 个代码问题并新增 1 个可复跑审计脚本”。

## 2. 需要完善的内容

| 编号 | 优先级 | 当前缺口 | 影响 | 完成标准 |

## 3. 实施工作包

### WP-01：真实模型接入与 `run_demo.bat` 闭环

**目标：** 让真实模型能够被一次命令启动、验证并留下可审计证据。

**修改范围：**

- `run_demo.bat`
- `ai-service/app/adapters.py`
- `platform/src/main/java/com/tracewitness/platform/agent/PythonAgentClient.java`
- `platform/src/main/resources/application.yml`
- `docs/deploy.md`
- `docs/api.md`

**具体任务：**

1. `run_demo.bat` 检查 `TRACEWITNESS_MODEL_BASE_URL` 和 `TRACEWITNESS_MODEL_NAME`。
2. API key 改为可选，支持本地 Ollama、vLLM 等无鉴权 OpenAI-compatible 服务。
3. 启动 Python `:8000`、Java `:8080`，等待 `/health` 和 `/api/health`。
4. 检查 `/api/mode` 返回 `MODEL_API`，若不是则失败。
5. 发起一次真实 smoke investigation，检查：
   - 至少一次真实工具调用；
   - 报告 `source_ids` 非空且全部属于本次 run；
   - 高风险动作 `executed=false`；
   - Agent 运行没有 `model_failed`。
6. 模型请求增加：
   - 连接和读取超时；
   - 429/5xx 有上限的指数退避；
   - 明确的 `model_timeout`、`model_rate_limited`、`model_bad_response` 分类；
   - 仅在没有副作用时重试。
7. 记录模型名称、耗时、轮次和供应商返回的 token usage，不记录 API key。

**验收：**

```powershell
$env:TRACEWITNESS_MODEL_BASE_URL='<OpenAI-compatible-url>'
$env:TRACEWITNESS_MODEL_API_KEY='<optional>'
$env:TRACEWITNESS_MODEL_NAME='<model-name>'
cmd /c run_demo.bat
```

期望退出码 `0`，页面显示 `MODEL_API`，工具调用和引用均来自同一次 run。

### WP-02：Agent 工具契约和固定评测集

**目标：** 把“Agent 能运行”升级为“Agent 能力可测量”。

**修改范围：**

- `contracts/tools/*.schema.json`
- `ai-service/app/adapters.py`
- `eval/agent/positive.json`
- `eval/agent/negative.json`
- `scripts/run_agent_eval.py`
- `docs/agent-eval-report.md`

**具体任务：**

1. 六个工具补齐 `description`、参数描述、使用条件和返回来源说明。
2. 建立 30 条正向任务：
   - 事件调查；
   - 事件详情；
   - 人员检索；
   - 轨迹构建；
   - 同行查询；
   - 证据导出；
   - 多工具组合；
   - 高风险动作请求；
   - 空结果和证据不足。
3. 建立 20 条反向任务：
   - 不存在的事件；
   - 没有同行；
   - 检索为空；
   - 不允许跨 run 引用；
   - 伪造引用；
   - 工具参数错误；
   - 高风险动作直接执行请求；
   - 模型返回非 JSON；
   - 模型超时；
   - 空工具结果不得编造结论。
4. 评测脚本分别支持 `MOCK`、本地 fake provider 和真实 provider，三组结果不得混算。
5. 每次运行固定场景、模型名、temperature、seed、轮次和超时。
6. 输出以下指标：
   - 任务完成率；
   - 工具选择准确率；
   - 引用合法率；
   - 反向断言通过率；
   - 高风险动作执行数，必须为 0；
   - 平均轮次；
   - P50/P95 延迟；
   - token 使用量；
   - 失败分类。

**建议目标值：**

| 指标 | 目标 |
| --- | --- |
| 引用合法率 | 100% |
| 高风险动作实际执行数 | 0 |
| 反向断言通过率 | 100% |
| 任务完成率 | 首轮记录基线，稳定后目标不低于 80% |
| 工具选择准确率 | 首轮记录基线，稳定后目标不低于 85% |
| P95 延迟 | 低于 Java 当前 60 秒读取超时，并记录供应商波动 |

引用合法率和高风险动作是硬门槛，不因模型能力不足而降低。任务完成率和工具选择准确率先测基线，再决定是否调整目标。

### WP-03：自动化质量门禁与 CI

**目标：** 不再依赖人工记得执行检查。

**修改范围：**

- `platform/build.gradle`
- `ai-service/requirements-dev.txt`
- `scripts/run_quality.ps1`
- `.github/workflows/ci.yml`
- `docs/quality-gates.md`

**建议工具：**

- Java：JaCoCo、SpotBugs、Checkstyle 或 PMD。
- Python：pytest-cov、Ruff、Bandit。
- 依赖：Gradle dependency report、`pip-audit`、Dependabot。
- 秘密扫描：Gitleaks。
- 仓库卫生：大文件检查、未跟踪私有资料检查、许可证清单检查。

**验收：**

1. Java 和 Python 测试全部通过。
2. 生成覆盖率报告；首轮先记录基线，之后禁止核心模块覆盖率下降。
3. 静态分析无 High/Critical。
4. 依赖扫描无未处置的 Critical；High 必须有书面豁免理由。
5. 密钥扫描无命中。
6. CI 在干净 Windows 环境执行通过。
7. `run_quality.ps1` 汇总所有检查，任一失败退出码非 0。

建议覆盖率门槛：

- 总体行覆盖率不低于 65%；
- `agent`、策略类、`store`、安全校验相关包不低于 75%；
- 新增代码必须有对应测试，不以总数替代覆盖质量。

### WP-04：HTTP 与浏览器端到端回归

**目标：** 把临时审计变成每次可复跑的回归。

**修改范围：**

- `scripts/http-audit.ps1`
- `scripts/run_e2e.ps1`
- `e2e/playwright.config.*`
- `e2e/tests/*.spec.*`
- `run_eval.bat`

**具体任务：**

1. 把人员审批、告警确认、插件回滚、难例标注、非法 JSON、404、重复操作 409 等 7 项有状态检查并入脚本。
2. 脚本自行使用临时数据库和临时媒体目录，避免污染 `data/local/`。
3. 增加 Playwright 浏览器回归：
   - 首页加载；
   - 无 console error 和 page error；
   - 事件、工具调用、证据包正常展示；
   - 证据校验成功和篡改失败；
   - 审批、告警确认、插件回滚；
   - 390px 下无横向溢出；
   - axe-core 无 violation。
4. `run_eval.bat` 增加 `TRACEWITNESS_HTTP_AUDIT=1` 和 `TRACEWITNESS_E2E=1` 开关。
5. CI 默认运行 HTTP 和浏览器回归。

**验收：**

```powershell
$env:NO_PAUSE='1'
$env:TRACEWITNESS_HTTP_AUDIT='1'
$env:TRACEWITNESS_E2E='1'
cmd /c run_eval.bat
```

任意单元、接口或浏览器检查失败时，命令必须返回非 0。

### WP-05：API、并发与数据一致性

**目标：** 收掉最容易在评审中暴露的工程问题。

**具体任务：**

1. 为审批、告警、证据、难例、插件回滚定义请求 DTO。
2. 开启未知字段拒绝，缺少必填字段返回 400。
3. 生成并提交 OpenAPI 文档，增加契约测试。
4. 增加本地 token：
   - 默认 token 由启动脚本生成或从环境变量读取；
   - 所有写接口要求 token；
   - 页面通过同源会话或请求头携带；
   - 未认证返回 401。
5. 所有写服务统一校验记录 `runId` 是否属于当前 run。
6. `nextId` 改为数据库原子分配，并增加并发测试。
7. `publishRemaining` 增加 `runId` 条件。
8. 为关键表补外键、唯一约束和必要索引；先做兼容迁移，不重写已有数据库。
9. 增加 H2/Flyway 空库迁移、旧库升级、重复迁移和失败回滚测试。

**验收：**

- 额外字段、错误类型、缺字段全部返回 400。
- 未认证写请求返回 401。
- 跨 run ID 写请求返回 404。
- 并发申请 1000 个 ID 无重复、无主键冲突。
- 发布 A run 的 outbox 后，B run 仍保持 `PENDING`。
- 全新数据库和上一版本数据库均可成功迁移。

### WP-06：可靠性、可观测性和恢复

**目标：** 证明系统不是只能成功跑一次的演示。

**具体任务：**

1. 增加失败注入：
   - 模型超时；
   - 模型 429/5xx；
   - 非法 JSON；
   - 工具异常；
   - AI 服务不可达；
   - 数据库写入失败。
2. 失败分类拆分：
   - `model_timeout`
   - `model_rate_limited`
   - `model_bad_response`
   - `tool_failed`
   - `persistence_failed`
   - `citation_invalid`
3. 结构化日志至少包含 `runId`、`agentRunId`、`toolName`、`stage`、`durationMs`、`failureType`。
4. 增加 `/api/health` 依赖状态或 `/api/ready`：
   - 数据库可用；
   - AI 服务可用；
   - 模型模式；
   - 版本和构建时间。
5. 增加重启恢复测试：
   - 启动、生成数据、停止；
   - 重新启动；
   - 数据、证据包和审批状态保持一致。
6. 增加数据库备份和恢复说明，至少提供文件级备份与恢复演练。

### WP-07：文档、演示和发布收口

**目标：** 让招聘方在 10 分钟内看懂、运行并验证项目。

**具体任务：**

1. 录制 5-10 分钟演示视频，只使用合成数据。
2. 视频明确标注当前是 Mock 还是真实模型。
3. README 增加“当前能力 / 未验证能力 / 一条命令启动 / 评测结果 / 已知限制”。
4. 修正文档中的口径冲突，例如 `architecture.md` 一处写模型适配器“只保留接口”，后文又写会发送真实请求。
5. 选择并添加 `LICENSE`，同步更新 README。
6. 添加 `THIRD_PARTY_NOTICES.md` 或依赖清单。
7. 生成最终 `docs/quality-report.md`，只引用可复跑命令的结果。
8. 简历描述只写已经实测的能力和指标。

## 4. 实施顺序与工作量

建议按以下顺序执行，避免先做展示后补核心证据。

| 阶段 | 工作包 | 预计工作量 | 产出 |
| --- | --- | --- | --- |
| 第 1 步 | WP-01 真实模型与 `run_demo` | 1.5-2 天 | 真实 smoke test、可启动演示 |
| 第 2 步 | WP-02 Agent 工具契约与评测 | 2-3 天 | 30+20 任务集、量化指标 |
| 第 3 步 | WP-03 质量门禁与 CI | 1-1.5 天 | 覆盖率、静态扫描、CI |
| 第 4 步 | WP-04 HTTP/浏览器回归 | 1-1.5 天 | 一条命令端到端回归 |
| 第 5 步 | WP-05 API、并发、数据一致性 | 1.5-2 天 | DTO、认证、原子 ID、迁移测试 |
| 第 6 步 | WP-06 可靠性与可观测性 | 1-1.5 天 | 失败分类、日志、恢复测试 |
| 第 7 步 | WP-07 文档、视频、许可证 | 1 天 | 可公开分享的最终交付 |

总计约 9-12 个工作日。若只追求“作品集可展示版”，至少完成 WP-01、WP-02、WP-04、WP-07；WP-03 和 WP-05 是专业评审认可度最高的加分项。

## 7. 不建议当前投入

以下内容会扩大范围，但对当前求职展示收益较低：

- 接入真实摄像头、门禁、电梯或厂商硬件。
